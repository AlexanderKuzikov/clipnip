# DECISIONS — ClipNip

## 001: Пересоздание ReClip на Go + WebView (2026-08-04)

**Статус:** принято

**Контекст:** ReClip (Flask + yt-dlp, веб-UI на localhost) требует Python/venv; джобы в памяти теряются при рестарте; ffmpeg-путь захардкожен под одну машину; загрузка в браузер — через blob-скачивание.

**Решение:** новый проект ClipNip — desktop-приложение на Go: один exe (~8 MB), UI — системный WebView2 через loopback HTTP (`127.0.0.1:0`), движок скачивания — yt-dlp как subprocess, bootstrap yt-dlp/ffmpeg при первом запуске.

**Почему:**
- 1000+ сайтов поддерживает yt-dlp — его не переписываем, только оркеструем (exec + парсинг прогресса).
- WebView2 встроен в Windows 10/11 — раздувание Electron (380 MB в опыте пользователя) не нужно.
- Один exe без установщика; зависимости подтягиваются автоматически.
- Файлы сразу на диске — «Открыть папку» вместо диалога сохранения.

**Trade-offs:**
- Убийство процессов на Windows — только taskkill /T /F: exec.CommandContext на этой машине (Go 1.26) не убивает процессы вообще (проверено).
- Прогресс yt-dlp идёт в stdout в формате `--progress-template` — парсер завязан на формат строк (coupling к CLI).
- Джобы in-memory: состояние теряется при рестарте (осознанно, для личного инструмента достаточно).

**Атрибуция:** ReClip by averygan — MIT; copyright сохранён в LICENSE, указан в README.

## 002: Встроенные шрифты вместо Google Fonts (2026-08-04)

**Статус:** принято

**Контекст:** `<link>` на fonts.googleapis.com в head блокировал первый рендер — при недоступности CDN (РФ) окно висело тёмным.

**Решение:** шрифты PT Serif/PT Mono (woff2, кириллица) вшиты в embed (`web/fonts/`), отдаются с `/fonts/`, `font-display: swap`; фон документа задан инлайн (`html { background: #f4f1eb; }`).

## 003: Офлайн-монобинарник — yt-dlp и ffmpeg вшиты в exe (2026-08-04)

**Статус:** принято

**Контекст:** изначально yt-dlp/ffmpeg скачивались при первом запуске (bootstrap с GitHub и gyan.dev). В РФ GitHub периодически блокируется, gyan.dev качается минутами — «один файл» не работал на чистой машине.

**Решение:** yt-dlp.exe и ffmpeg.exe сжаты gzip и вшиты в exe через `go:embed` (`embedded/*.gz`). При первом запуске распаковываются в `%LOCALAPPDATA%\clipnip\bin\` (1-2 сек). Существующие файлы на диске не перезаписываются — возможна ручная замена свежего yt-dlp без пересборки. ffprobe исключён (не используется). Итоговый exe ~60 MB.

**Альтернативы:** оставить bootstrap (не офлайн); хранить бинарники отдельными файлами рядом с exe (не «один файл»).

**Trade-off:** обновление yt-dlp требует пересборки (или ручной замены в bin); репо +~54 MB (gzip-архивы).

## 004: Модель управления загрузками — состояния, приоритеты, адаптация (2026-08-04)

**Статус:** принято

**Контекст:** плейлисты до 500 позиций на нестабильном YouTube: массовые 403/429, «мёртвые» ссылки забивали очередь, паузы гонялись с ретраями, all-кнопки висли (deadlock).

**Решение:**
- Машина состояний джоба: `queued → downloading → done|error|cancelled`, плюс `paused` (kill + .part), `retry_wait` (backoff 5с×N, до 2 повторов, потолок суммарно 90 с).
- Две очереди: `jobQueue` (новые) и `retryQueue` (приоритетная — упавшие/резюмированные раньше новых).
- Адаптивная параллельность: старт 8, потолок 10, пол 1; +1 за 15 успешных; ÷2 при сетевом отказе; cooldown 30 с (429) / 15 с (403) блокирует ВСЕ новые старты.
- Защита от гонок: `claim()` (один запуск), маркированные ошибки `killed: paused`, onProgress не перетирает paused/cancelled.
- Watchdog 60 с без роста байтов → kill + error «Download stuck».
- Классификация: fatal (private/removed/404/регион/unavailable) не ретраится; 403/429/5xx/timeout/stalled — ретраится.

**Альтернативы:** фиксированный пул (не переживает штормы 429); одна очередь FIFO (мёртвые ссылки блокировали живые — наблюдали).

**Trade-off:** параллельность ≠ строгий порядок (завершения вразнобой); «Video unavailable» считается fatal — временно-заблокированные в РФ ссылки не ретраятся (осознанный компромисс ради живости очереди).

## 005: Пропуск уже скачанных файлов — по имени файла, не по архиву yt-dlp (2026-08-04)

**Статус:** принято

**Контекст:** повторное добавление плейлиста (200+ песен) перекачивало всё заново: `renameTo` защищал от перезаписи суффиксом `(1)`, но дубли плодились, сеть и очередь тратились впустую.

**Решение:** перед запуском yt-dlp (title уже известен из /api/info или fetchTitle) проверяется наличие в папке загрузки файла `sanitizeFilename(title)` + одно из расширений режима (`preferredExts`: video — .mp4/.mkv/.webm, m4a — .m4a/.webm/.opus, mp3 — .mp3/...). Нашёлся — джоб в терминальный статус `skipped` (File/Filename = существующий файл), без сети. Счётчик считает skipped как completed. «Download anyway» — одноразовый флаг `force` в /api/download, обходит проверку.

**Почему не `--download-archive` (нативная фича yt-dlp):**
- Архив глобальный, не привязан к папке загрузки — смена папки не меняет семантику «уже скачано».
- Первый запуск слеп к файлам, скачанным до включения фичи (главный сценарий — существующая медиатека).
- Архив не различает режимы: скачал mp3 → запрос mp4 того же видео будет пропущен (лечилось бы отдельным архивом на режим — усложнение).
- Пропуск происходил бы внутри yt-dlp: пришлось бы отличать «пропущено» от «final file not found» по выводу процесса.

**Trade-offs:**
- Детект по имени хрупок: переименованный/перенесённый вручную файл не находится (осознанно; без БД по URL не решить).
- Проверка на старте джоба, а не при добавлении: карточка успевает мелькнуть статусом downloading.
- Коллизии `Title (1).ext` существующими не считаются — матчится только каноническое имя.

## 006: Вшитый yt-dlp с маркером версии (2026-10-07)

**Статус:** принято

**Контекст:** вшитый yt-dlp `2026.07.04` перестал качать: extractor отрабатывает, но видеопоток с googlevideo отдаёт `HTTP Error 403: Forbidden` (дефолтный клиент `android_vr` YouTube отключил). Ретраи и cooldown в jobs.go лечили симптом, а не причину. Второй баг: `ensureBins` распаковывает ffmpeg в `binDir`, но `--ffmpeg-location` не передаётся — склейка видео+аудио работала только потому, что ffmpeg был в PATH.

**Решение:**
- Вшитый yt-dlp обновлён; канал — **nightly**, см. поправку обоснования ниже.
- `extractEmbedded` для yt-dlp сверяет константу `ytdlpVersion` с маркером `yt-dlp.exe.ver` рядом с бинарником: смена версии в embed → принудительная перераспаковка. Раньше файл на диске не перезаписывался никогда, то есть обновление бинарника не доезжало до уже установленного приложения.
- `--ffmpeg-location <binDir>/ffmpeg.exe` передаётся в `runYtDlp`, если файл есть. Приложение больше не завязано на ffmpeg в PATH.

**Поправка к обоснованию (открыто и исправлено в той же сессии).** Первая редакция этого ADR отвергала nightly с двумя доводами, и **оба были неверны**:

1. «Ассеты nightly удаляются через неделю, монобинарник их не переживёт» — неправда. Теги nightly-builds хранятся месяцами. Но главное: как только бинарник вшит в exe под gzip, существование апстрим-ассета **вообще не имеет значения** — ты замораживаешь снапшот. Довод был невнимателен к собственному механизму embed.
2. Настоящая причина, по которой выбран nightly, противоположна той, что была записана: сам README yt-dlp говорит, что stable-канал «часто устаревший и склонный к внешним поломкам» и рекомендует nightly обычным пользователям. Наш проект борется именно с поломками от изменений на стороне YouTube, поэтому свежие player-клиенты нужны здесь больше, чем где-либо ещё.

**Проверка перед переключением:** nightly `2026.09.27.232945` прогнан на этой машине — список форматов, скачивание и склейка дали результат, идентичный stable (тот же файл 153.7 MB).

**Альтернативы:**
- Перезаписывать бинарник всегда — минус распаковка ~18 МБ gzip на каждом старте.
- Сверять `yt-dlp --version` через subprocess — точнее, но это запуск ~2 с на каждом старте только ради проверки. Маркер в файле дешевле и достаточен: он меняется тем же коммитом, что и сам бинарник.

**Trade-offs:**
- `ytdlpVersion` в коде надо поднимать руками вместе с заменой `.gz` — рассинхрон возможен, но проявится лишней перераспаковкой, а не поломкой.
- Nightly несёт непроверенные изменения. Потолок цены ограничен: плохой снапшот валится сразу и громко, а предыдущий вернуется одним коммитом; версия движка видна в подвале UI и в логе, поэтому «поехавшая» сборка заметна сразу.

## 007: Таксономия ошибок — 403 это не перегрузка (2026-10-07)

**Статус:** принято

**Контекст:** все 403 сводились к одному классу «перегрузка»: ретраи, cooldown 15 с, деление параллельности пополам. Причины у 403 принципиально разные, и лечатся они противоположно:

| Наблюдение | Причина | Что делать |
|-----------|---------|------------|
| `HTTP Error 429` | троттлинг | ждать, резать параллельность |
| `unable to download video data` после `[info] Downloading 1 format(s)` | движок устарел: extractor отработал, поток не отдали | ничего не ретраить, сказать «пересобери» |
| `Sign in to confirm you're not a bot`, 403 на этапе extractor | сайт отказал небраузерному клиенту | cookies; **параллельность не трогать** |
| таймаут / 5xx | сеть | ретрай, резать параллельность |

Проверено вживую: `GET https://x.com/` из пустого профиля браузера отдаёт HTTP 403 при полностью рабочей сети. Приложение на такой домен деградировало пул параллельности до единицы без шанса на восстановление — то есть само маскировало настоящую причину (устаревший движок) под видом «YouTube перегружен».

**Решение:**
- Классы: `throttle` / `engine` / `site` / `fatal` / `network`. Функции `retriable` и `affectsParallelism` разведены: engine и fatal не ретраятся, параллельность и cooldown трогают **только** throttle и network.
- `unable to download video data` проверяется **первым**: строка встречается только в загрузчике, то есть после успешного extractor — самодостаточный признак безостановочной оглядки на предыдущие строки лога.
- Отдельное поле `error_hint` с actionable-текстом. Сырой текст yt-dlp в UI больше не разбирается браузером.
- Проба транспорта (`netprobe.go`) смотрит **только DNS и TCP**. HTTP-статус в проверку не входит: 403 от сайта нельзя отличить от 403 провайдера, и совет «включи VPN» на уже включённом VPN — вредный. Если задан `HTTP(S)_PROXY`/`ALL_PROXY`, проба отказывается давать вердикт, а не гадает по прямому соединению.

**Альтернативы:**
- Оставить один класс и лечить все 403 одинаково — отвергнуто: это и было причиной, по которой баг с движком жил месяц.
- Строить пробу на HTTP-запросе к целевому домену — отвергнуто: 403/Cloudflare от небраузерного клиента неотличим от сетевой блокировки.
- Возвращать 403 с пробой как «заблокировано» жёстко, без учёта медленных сетей — отвергнуто: даёт ложные блокировки на живых, но медленных соединениях. Сначала ждём вердикт пробы, потом yt-dlp (45 с), так что на живом домене выигрыша почти нет, а на заблокированном — 45 с → секунды.

**Побочный эффект:** убран двойной лог финального фейла (retry-лог + финальный) и `cooldown403` как отдельная константа — теперь один cooldown на троттлинг.

### Поправка к ADR 007: класс `engine` был ложным диагнозом (2026-10-07, позже в тот же день)

Первая редакция объявляла `unable to download video data` доказательством устаревшего движка. На живом прогне это **обернулось ложью**: пользователь увидел «Engine too old to fetch this stream» на nightly `2026.09.27` — то есть на самом свежем движке, который существует. Утверждение «движок устарел» проверяемо, и оно было проверяемо ложным.

Две ошибки, одна наша, другая в исходном сигнале:

1. **Строка не различает компоненты.** yt-dlp выводит `unable to download video data` от своего HTTP-загрузчика независимо от того, что качает — видео или аудио. При отказе на втором компоненте сообщение то же самое. Из лога: видео 1080p докачано до 1.14 ГБ, стартует `.f140.m4a`, падает — и ClipNip писал про «движок».
2. **Одна сигнатура ≠ одна причина.** 403 на передаче бывает от устаревшего движка, от репутации адреса (смена VPN, исчерпанный лимит на IP) и от истёкшей подписи на очень большом файле. Подпись googlevideo-URL содержит адрес клиента, поэтому смена VPN посреди скачивания ломает передачу.

**Решение:**
- Класс переименован `engine` → `stream` — называть то, что наблюдается («передачу отказали»), а не догадку о причине.
- Утверждение проверяется состоянием: константа `ytdlpKnownGoodSince` (последняя сборка, работающая с текущими player-клиентами) и сравнение с реально запущенной версией через `versionDate`. Если версия не выяснилась — не обвиняем движок вообще: неизвестность не повод для утверждения.
- Если движок свежий, подсказка называет настоящее: адрес, смена VPN, истёкшая подпись — и говорит, что повтор продолжит с уже скачанного (`partialBytes`).
- Stall-сообщение тоже упоминает VPN: обрыв туннеля выглядит ровно так же.

**Вывод для будущих правок:** приложение не должно утверждать причину, которую не может проверить. Симптом — да, причина — только с опорой на собственное известное состояние.

## 008: Cookies — три уровня свободы вместо списка браузеров (2026-10-07)

**Статус:** принято

**Контекст:** часть сайтов отдаёт неавторизованному клиенту 403 — X так делает для анонимных запросов. Свой механизм cookies в Go означал бы писать расшифровку DPAPI, SQLite-парсер и гонку с блокировкой файла браузером. Всё это уже сделано в yt-dlp.

Ключевая находка в исходниках `yt_dlp/cookies.py`: спецификация принимает **не только имя браузера, но и путь**:

```python
elif _is_path(profile):
    search_root = profile
    config['browser_dir'] = os.path.dirname(profile)   # отсюда берётся Local State
```

Значит для **любого** Chromium-форка работает `chromium:<каталог-профиля>` — Yandex.Browser, CentBrowser, Iridium, Comodo Dragon, Amigo, 7Star. Перечислять их не нужно.

**Решение — три уровня, от удобного к универсальному:**

1. **Автоопределение.** Сканируем пути из исходников yt-dlp, показываем найденные браузеры и профили (свежий первым — так же, как выбирает сам yt-dlp без профиля). Пути: `%LOCALAPPDATA%\Google\Chrome\User Data`, `%LOCALAPPDATA%\Microsoft\Edge\User Data`, `%APPDATA%\Opera Software\Opera Stable` (профилей не поддерживает), `%APPDATA%\Mozilla\Firefox\Profiles` + MSIX-каталог Store-версии.
2. **Свободная строка** `браузер:профиль` — passthrough в yt-dlp. Покрывает все не-listed браузеры.
3. **Файл `cookies.txt`** через `--cookies` — когда формат вообще другой.

Уровни 1 и 2 складываются: yt-dlp сам объединяет обе банки (`load_cookies` мержит jar'ы). Собственной криптографии в ClipNip — ноль.

**Почему не cookies.txt как основной путь:** он оставляет на диске открытый файл со всеми сессионными токенами бессрочно. Чтение DPAPI-базы привязано к профилю Windows, токены на диск не попадают. Поэтому файл — только запасной вариант.

**Критичное следствие, найденное в исходниках:** на ошибке расшифровки DPAPI yt-dlp поднимает `DownloadError` с комментарием «force exit» — то есть **падает весь процесс**, а не только чтение cookies. Включённые cookies способны сломать скачивание вообще всего, включая обычный YouTube. Отсюда:
- кнопка «Test» — часть контракта, а не украшение;
- два задокументированных сбоя (занятая база — issue 7271, сбой DPAPI — issue 10927) переводятся на человеческий язык.

**Безопасность:**
- Спецификация браузера попадает в argv — валидируется белым списком, мусорный `config.json` не превращается в аргументы yt-dlp.
- Значения cookies в приложение не попадают и в лог не пишутся.
- Предупреждение при первом включении обязательно: чтение чужого хранилища учётных данных — другое решение о доверии, чем «скачай видео». Текст намеренно точный, а не пугающий.

**Trade-offs:**
- Детект дублирует пути из yt-dlp (связь с версией движка). Расхождение безвредно: значения всё равно уходят в yt-dlp, а свободная строка страхует.
- `errorHint` для класса `site` различает включённые и выключенные cookies — иначе совет «включи cookies» уводит по кругу (обнаружено на живом прогоне).
- Cookies глобальны, а не per-URL. Это безопасно: yt-dlp сам привязывает cookies к домену, чужому сайту они не уйдут.

## 009: Вшитый deno — нужен, но не тем способом, которым думали (2026-10-07)

**Статус:** принято

**Контекст:** yt-dlp требует JS-рантайм для yt-dlp-ejs (JS-челленджи YouTube). По умолчанию включён **только deno**, и берётся он из PATH.

**Решение:** вшит deno 2.9.7 (`embedded/deno.exe.gz`), версия константой `denoVersion` + маркер `deno.exe.ver` — тем же механизмом, что и для yt-dlp. Во все три вызова добавлен `--js-runtimes deno:<binDir>`.

**Что показали замеры — и почему это стоило 42 МБ:**

- deno.exe = 97.5 MB, gzip даёт 42.6 MB (файл уже упакован, сжатия почти ноль). exe вырос с 63 до 101 MB.
- На этой машине **нет ни node, ни bun, ни quickjs** — yt-dlp прямо пишет `node (unavailable)`. То есть без вшитого deno JS-рантайма не существовало бы вообще, и я предложенный в обсуждении «дешёвый вариант» `--js-runtimes deno,node,bun` дал бы ровно ничего.
- **Опровержение моей же гипотезы:** yt-dlp находит deno и **без** флага — он ищет рантайм рядом со своим собственным exe, а binDir это и есть каталог с yt-dlp. То есть `--js-runtimes` — страховка от смены этого поведения, а не необходимое условие. Зафиксировано комментарием в коде, иначе будущий мейнтейнер будет искать несуществующую причину.

**Снят принудительный `--no-playlist`** из `/api/info`. Причина: yt-dlp сам различает ссылку на одно видео и страницу с несколькими (один элемент → одно видео), а флаг молча урезал любую не-YouTube страницу с несколькими роликами до одного — без ошибки и без предупреждения. `--flat-playlist` оставлен только для распознанных ссылок на плейлист YouTube, где он нужен для скорости на 500 позициях.

**Побочно:** `buildQualityList` больше не выбирает формат по одному лишь max tbr. С появлением HLS у m3u8 битрейт всегда выше, а `total_bytes` у него иногда NA — прогресс-бар терял точность. При равной высоте https-DASH теперь предпочтительнее.

**Trade-offs:**
- +42 МБ к exe за профилактику. Оправдано тем, что на этой машине альтернативы не было, а негибкость подтверждена замером.
- Снятие `--no-playlist` теоретически может заставить полное извлечение большой не-YouTube страницы. Ограничено существующим таймаутом `/api/info` (45 с) и понятным сообщением пользователю. **Не проверено на реальных страницах X/Facebook/xv-ru — URL'ов от пользователя не было.**
- Часть высот теперь отдаётся как «(alt)» (VP9/AV1 в webm): там на той же высоте https-вариант существует только в webm. Мерж в mp4 даёт файл, который понимают не все плееры — честно помечено в UI.

## 010: Надёжность — счётчики по компонентам, очередь на диске, один экземпляр (2026-10-07)

**Статус:** принято

**Контекст:** четыре разнородных дефекта, найденных при перечитывании кода и на живых прогонах.

**1. Счётчики прогресса при склейке показывали размер последнего компонента.** yt-dlp качает видео и аудио отдельными файлами, каждый со своими счётчиками с нуля. Последний тик относился к аудиофайлу, поэтому карточка писала «9.8 MB» для файла в 153.7 MB. Первая попытка починки (просто суммировать) дала свой баг: `Total` не выставлялся для первого компонента, то есть прогресс-бар стоял на нуле всё время.

**Решение:** явная схема — `CurTotal`/`CurDownloaded` (текущий компонент) и `DoneTotal` (сумма завершённых). Начало нового компонента определяется откатом `downloaded_bytes`; в UI уходят агрегаты `DoneTotal + Cur*`. Скорость при `NA` от yt-dlp считается по дельте байтов (заодно закрыт пропуск `B/s` в парсере — yt-dlp печатает сырые байты при скорости ниже 1 KiB/s).

**2. Очередь терялась при рестарте.** ADR 001 сознательно отказался от персистентности состояния — но это была не та цена, за которую платили: терялась не «стадия джобы», а сам состав пачки, то есть перезапуск посреди «Download All» означал вставлять всё заново.

**Решение:** на диск пишется **состав** очереди (`queue.json`: url, mode, format_id, title) — не стейт-машина. После рестарта джобы возвращаются в `queued` и докачиваются через `.part`, который и так переживает перезапуск. Обновление файла — в трёх точках: `defer persistQueue()` в `runDownload` (накрывает done/error/skipped/cancel/panic одним хуком), `cancelJob` и постановка в очередь. Пустая очередь удаляет файл.

**3. Два экземпляра делили папку загрузки.** Два пула воркеров на один каталог = коллизии в `.part`.

**Решение:** именованный mutex `Local\ClipNip.SingleInstance`. В GUI-режиме — модальное окно, в headless только лог: модалка в headless висела бы вечно, что и случилось на первом же прогоне.

**4. `.part` жил 24 часа.** Поставленная на паузу загрузка большого файла терялась при возвращении через пару дней — докачивать было нечего. TTL поднят до 7 дней.

**5. Лог-шум и неверная метка ретрая.** Финальный фейл больше не дублируется; cooldown пишется один раз на смену, а не по строке на каждого заблокированного воркера; потолок retry меряет **суммарное ожидание между попытками** (`RetryWait`), а не «время с первого ретрая» — в прежнюю метку попадало ожидание слота в очереди, из-за чего джоб с двумя короткими ретраями выглядел как «13m».

**Побочно:** лог открывается из UI (`/api/log` — хвост в модалке и кнопка «открыть файл»): диагностика больше не требует захода в AppData.

**Trade-offs:** персистентность очереди вводит состояние на диске, которое надо переживать при обновлении формата файла — отсюда валидация записей при восстановлении (мусорные URL и режимы отбрасываются). Скорость по дельте байтов сглаживает всплески (обновление раз в ~1.5 с) и не работает для одиночного тика.

## 011: Компоненты с сервера вместо вшитых PE (2026-10-07)

**Статус:** принято

**Контекст:** повод — ложные срабатывания антивирусов на VirusTotal. Пока ClipNip является одним файлом, который при запуске распаковывает PE и запускает его, сигнатурные срабатывания не уходят принципиально: PE-внутри-PE + распаковка во время работы = сигнатура дроппера.

**Ошибочная предпосылка, из-за которой всё до этого делалось.** AGENTS.md предписывал вшивать компоненты, потому что «GitHub/gyan.dev блокируются в РФ». Пункт унаследован из ранних решений и **ни разу не переосмыслен**. Он опирался на источник, а не на подход: офлайн у утилиты, тянущей из сети, не имеет почти никакого смысла — без сети она всё равно ничего не скачает. Своим сервером блокировка снимается сама, и необходимость вшивать исчезает.

**Решение — две сборки, автономность перестаёт быть обязательной:**

| Сборка | Размер | Встроено PE |
|---|---|---|
| по умолчанию | ~107 МБ | 3 |
| `-tags clipnipremote` | **~8.1 МБ** | **0** |

**Порядок разрешения компонента:** `clipnip-bin` рядом с exe → кэш `%LOCALAPPDATA%\clipnip\bin` → встроенная копия → сервер. Позволяет переносимую поставку без сети, кэш как ускорение и автономность без зависимости от сервера.

**Обязательные компоненты — только yt-dlp и ffmpeg.** deno выведен в опциональные: он страховка для машин без JS-рантайма, а не условие работы (проверено — видео 153.7 МБ со склейкой скачивается без него). Раньше он считался обязательным, что держало +42 МБ в каждой сборке.

**Безопасность загрузки:**
- только https: манифест с хешем приходит по тому же каналу, что и файл, поэтому без TLS сверка не значит ничего;
- установка атомарная — файл сначала во временное имя, хеш считается на лету, и только при совпадении `rename`. Повреждённая загрузка никогда не становится рабочим бинарником;
- манифест версионируется, неизвестная версия и запись без 64-символьного хеша отвергаются.

**Trade-offs и пойманные при этом ошибки:**
- exe остаётся зависимым от доступности компонентов. Лечится portable-режимом и кэшем.
- Отказоустойчивость: без компонентов приложение **поднимается** и показывает статус, вместо того чтобы падать. Первая версия делала это фатальным — и тогда окно с ошибкой просило «укажите адрес сервера в настройках», в которые попасть было невозможно. Скриншот с этого окна и вскрыл противоречие.
- Вызовы yt-dlp строились путь в кэше напрямую, поэтому portable-папка находилась, а запускалась пустая кэш-копия. Пути переведены на реестр разрешённых компонентов (`componentPath`/`ytdlpPath`).

## 012: Сборка без логики загрузки — против ложных срабатываний (2026-10-07)

**Статус:** принято (эксперимент, результат замеряется на VirusTotal)

**Контекст:** remote-сборка из ADR 011 убрала встроенные PE, но Bkav Pro продолжает помечать exe: `1/70`, `W32.Malware.55B64109`.

**Что это за имя — установлено, а не выдумано.** `W32.Malware.*` — обобщённая ML-корзина Bkav Pro, родственник печально знаменитого `W32.AIDetectMalware`. За суффиксом не стоит конкретный образец вредоноса. Тот же флаг получают Electron-приложения без единой функции загрузки и инсталляторы с пустым содержимым. Отдельно важно: **замеренный базовый уровень для Go-приложений на Windows — 1–5 срабатываний из 70–71** (обычный «Hello World»); мы стоим на 1/70, то есть на полу инструмента.

**Гипотеза, которую надо было проверить, а не принять:** «exe сам скачивает исполняемый файл и запускает его» — паттерн дроппера, на который реагируют эвристики.

**Решение — третья сборка, отличающаяся от remote одной константой:**

| Сборка | Размер | Встроено PE | Загрузка с сервера |
|---|---|---|---|
| по умолчанию | ~107 МБ | 3 | да |
| `-tags clipnipremote` | ~8.1 МБ | 0 | да |
| `-tags clipnipportable` | **~7.6 МБ** | 0 | **нет вообще** |

`allowRemoteFetch` (`fetchflag_off.go` / `fetchflag_on.go`) делает ветку загрузки **недостижимой на этапе компиляции**, поэтому линкер выкидывает `loadManifest` и `downloadComponent`. Проверено строками, а не размером:

| строка | remote | portable |
|---|---|---|
| `manifest.json` | 1 | **0** |
| `unsupported manifest version` | 1 | **0** |
| `components URL must be https` | 1 | **0** |
| `http.Client` | 2 | **0** |
| ссылок на `net/http` | 1723 | 1114 |

**Что осталось и почему это не отвлекает:** `net/http` нужен для loopback-сервера интерфейса, `CreateProcessW` — для запуска самого yt-dlp. Это и есть работа программы; убрать их нельзя, не сломав ClipNip.

**Trade-offs:**
- Portable-сборка требует `clipnip-bin` рядом с exe — это честный офлайн-переносной комплект (exe + 3 файла), а не один файл.
- Обновление движка в ней — замена файлов в папке, а не прогон updater-а на сервере.
- **Ожидаемый выигрыш не доказан.** Замер выше показывает, что паттерн удалён из бинаря, но сработает ли на это ML Bkav — вопрос к измерению. Если флаг останется, вопрос закрыт: кодом 1/70 не берётся, и остаются подпись и исключение на стороне пользователя.

## 013: Постоянная панель навигации по папкам (2026-11-02)

**Статус:** принято

**Контекст:** выбор папки загрузки был текстовым полем с модальным `SHBrowseForFolderW`. В MuteNip та же задача решена постоянной ленивой панелью дисков и подпапок: навигация без диалогов, выбранная папка подсвечена.

**Решение:** перенести контракт `fs.go` из MuteNip — `GET /api/fs/drives` (локальные диски; сетевые и неизвестные отсекаются по `GetDriveTypeW`) и `GET /api/fs/list?path=` (подпапки, скрытые и системные исключены). В UI — левая панель с ленивым деревом; клик по папке сохраняет `download_dir` через существующий `/api/settings`. Модальный Browse из интерфейса убран, API-метод оставлен для совместимости.

**Trade-offs:**
- Сетевые диски в дереве не видны. Для загрузки в сетевую папку остаётся ручной ввод через API; в UI это осознанно не выпячивается.
- Дерево кэшируется на время сессии: новые папки появляются после refresh.
- Панель меняет раскладку: на узком окне уезжает наверх, на широком — постоянная колонка.

## 014: Режим «видео без звука» (2026-11-02)

**Статус:** принято

**Контекст:** нужен файл без аудиодорожки, но не «немой» плеер, а честный контейнер без аудиопотока.

**Решение:** новый режим `video_noaudio`. При выборе качества используется только видеоформат (`<id>`), при дефолте — `bestvideo…/best`. Так как у части сайтов единственный доступный формат мультиплексный (X: прогрессивные `http-*` содержат аудио), после скачивания ffmpeg проверяет наличие аудио и при необходимости пересобирает файл `-map 0 -map -0:a -c copy` без перекодирования. Имя получает суффикс ` (no audio)`, чтобы skip-детект не путал его с полным видео.

**Trade-offs:**
- Для мультиплексного источника аудио всё равно скачивается и затем отбрасывается — экономия трафика меньше, чем у video-only.
- Нужен ffmpeg (он и так обязателен для склейки и MP3).
- Постобработка — ещё одна копия файла на диск; на очень больших файлах заметна по времени.

## 015: Резолв компонентов один раз за процесс и защита loopback-API (2026-11-02)

**Статус:** принято

**Контекст:** второй прогон ревью показал две системные проблемы. `ensureBins` вызывался из каждого `runYtDlp`/`infoJSON`: это HTTP-запрос манифеста и SHA-256 ~215 МБ на каждую задачу, а параллельные воркеры одновременно пересоздавали `resolvedPaths` и писали `componentStates` без блокировки. Loopback-API принимал cross-origin POST с `text/plain` без preflight, включая `/api/components` (подмена сервера компонентов = загрузка и запуск exe).

**Решение:**
- резолв — одна операция под `componentsMu`; явный refresh из настроек; `resolvedPaths` заменяется атомарно целиком; манифест не грузится, если portable/embed уже содержат всё нужное;
- `sameOrigin` проверяет Host (`127.0.0.1`/`localhost`/`::1`) и Origin, а также `Sec-Fetch-Site: cross-site`; это закрывает CSRF и DNS rebinding;
- тесты уводятся в temp через `CLIPNIP_DATA`/`configDirOverride`, включая очередь и лог;
- `errBuf` защищён мьютексом (stderr-горутина `os/exec` и основной цикл писали одновременно);
- stall-детект считает postprocess-строки активностью, чтобы не убивать ffmpeg на склейке/извлечении звука.

**Trade-offs:**
- Обновление компонентов с сервера применяется на старте или по кнопке Apply, а не в середине очереди.
- Проверка Host ломает доступ к API через произвольный hostname; это осознанно, WebView ходит на 127.0.0.1.

## 016: Создание папок в панели навигации (2026-11-02)

**Статус:** принято

**Контекст:** в панели можно было только выбрать существующую папку. Для сценария «скачать в новую подпапку» приходилось выходить в проводник.

**Решение:** `POST /api/fs/mkdir` с `{parent, name}`. Создаётся ровно одна папка через `os.Mkdir`; `parent` обязан быть абсолютным существующим каталогом. Имя валидируется как trust boundary: запрещены разделители и спецсимволы Windows, `.`/`..`, ведущая точка, хвостовые точка/пробел, зарезервированные имена (`CON`, `NUL`, `COM1`…) и длина больше 120 рун. В UI — кнопка `new folder`, inline-форма с Enter/Escape; созданная папка сразу становится `download_dir` и раскрывается в дереве.

**Trade-offs:**
- Нельзя создать несколько уровней за один раз и нельзя создать скрытую папку с ведущей точкой.
- Ошибки показываются в inline-заметке, а не модальным окном; длинные системные сообщения могут обрезаться визуально.
- Создание идёт от имени пользователя и подчиняется его правам доступа; специального обхода ACL нет.
